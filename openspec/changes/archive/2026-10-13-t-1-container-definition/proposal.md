# Proposal

## Why

Контейнеры пока не имеют формальных требований, а связь сущностей с контейнерами-держателями,
аутентификация обращений, права управления и проверка доступа по дереву
зафиксированы только в
[requirements.md](requirements.md). Нужно оформить согласованные предметные
решения в проверяемые требования OpenSpec, чтобы последующее проектирование и
реализация одинаково трактовали адресацию, область управления и итог проверки
доступа субъекта. Для проверки доступа выделяется домен `authorization` с
capability `authorization/access-check`.

## What Changes

- Определить дерево контейнеров с типами `organization`, `environment`, `system`
  и `module`: порядок типов вдоль пути строго сохраняется, уровни можно
  пропускать без создания пустых контейнеров, корень может иметь любой из этих
  типов. Обратный порядок и повторение типа вдоль пути запрещены; несколько
  детей одного типа у общего родителя допустимы.
- Зафиксировать единственного контейнера-держателя каждого субъекта, объекта
  и модели доступа. Использование сущности моделью другого контейнера
  сохраняет её контейнера-держателя. Термин «владелец контейнера» обозначает
  вызывающего с полными правами управления этим контейнером и его потомками.
- Допустить `0..N` моделей доступа в контейнере: наличие модели необязательно,
  контейнер может содержать ноль, одну или несколько моделей.
- Определить ключ контейнера как текстовую строку, а составной ключ — как путь
  от корня через ключи контейнеров. Составные ключи в Tamarix уникальны и
  однозначно идентифицируют контейнеры.
- Разделить обращения на проверку доступа субъекта и управление моделями
  доступа, субъектами и объектами. В обоих типах вызывающий указывает
  составными ключами адресуемый контейнер `C` и представляемый контейнер `O`,
  от имени которого действует, и проходит аутентификацию по сертификату.
  DN сертификата должен быть приписан к `O` в Tamarix. Успешной сертификатной
  аутентификации и зарегистрированной привязки DN к заявленному `O` достаточно,
  чтобы признать вызывающего владельцем `O`; дополнительная административная
  роль не требуется.
- Зафиксировать полные права владельца на управление моделями и сущностями
  `O` и всех его потомков. Адресуемый контейнер `C` совпадает с `O` или является
  его потомком; контейнер-держатель управляемых данных `D` совпадает с `C` или
  является его потомком. Владелец `O` может обращаться непосредственно к
  потомку `D`. Управление через предка `O` или соседнюю ветку недопустимо,
  в том числе для данных самого `O`. При управлении сохраняются единственные
  держатели сущностей и моделей и ограничения использования сущностей в моделях.
- Определить область использования сущностей моделью контейнера `M`: субъекты
  имеют держателями `M` или его предков, объекты — `M` или его потомков. Область
  определяется реальными связями дерева, действует при пропущенных уровнях и
  исключает соседние ветки. Если субъект запроса вне допустимой области модели,
  её результат для этого запроса нейтрален; ограничения использования сущностей
  в самой модели сохраняются.
- При проверке доступа передавать ключ проверяемого субъекта; его доступ
  определяется моделями для субъекта, объекта и действия. Права владельца
  представляемого контейнера не дают автоматического разрешения субъекту.
  Адресуемый контейнер `C` совпадает с контейнером-держателем объекта `R` либо
  является его предком. Это условие относится к `C`. Дополнительного
  ограничения между субъектом запроса и `C` нет; область субъекта проверяется
  отдельно для каждой модели.
- Рассматривать все модели всех существующих контейнеров на пути от корня
  дерева до `R`, включая оба конца и предков `C`, даже когда `C` совпадает с
  `R`. Для каждой модели сохраняются её ограничения использования сущностей;
  модели соседних веток не участвуют.
- Определить объединение подходящих правил внутри каждой модели: любой запрет
  имеет приоритет над разрешениями; при отсутствии запретов хотя бы одно
  разрешение даёт разрешение; отсутствие подходящих правил для субъекта,
  объекта и действия даёт нейтральный результат. Это три определённых результата
  модели; нейтральный результат не влияет на решения других моделей.
- Считать неопределённый результат отдельной модели нейтральным при объединении
  результатов установленного полного состава цепочки, в том числе когда ошибка вычисления или недоступность
  необходимых данных не позволяют определить результат этой модели. Такой
  результат не отменяет известное разрешение или запрет других моделей.
- Запрещать доступ при невозможности установить полный путь до контейнера
  объекта или полный набор моделей хотя бы одного контейнера пути, даже если
  доступная часть моделей разрешает. Неизвестный состав отличается от
  неопределённого результата отдельной известной модели.
- Определить объединение результатов моделей при установленном полном
  составе цепочки: любой запрет
  запрещает доступ; при отсутствии запретов хотя бы одно разрешение разрешает
  доступ, в том числе при наличии неопределённых результатов других моделей.
  Если результаты только нейтральные и/или неопределённые, доступ запрещён по
  умолчанию. Отказ по умолчанию действует и при всех неопределённых результатах,
  и при отсутствии моделей на всём пути от корня до контейнера объекта.
- Распределить требования между `containers`, `authorization/access-check`
  и entity capabilities. Домен `authorization` охватывает только проверку
  доступа субъектов; управление моделями и сущностями остаётся в `containers`.
- Закрепить принятую карту ответственности: отдельный сервис контейнеров —
  дерево, ключи и DN; entity-сервисы — сущности и их держатели;
  `policy-adm-api` — модели, держатели, ссылки и полный набор моделей;
  `policy-decision-api` — сбор цепочки и вычисление доступа.
  Административные сервисы проверяют область управления по данным сервиса
  контейнеров; `access-assignment-api` в T-1 не затрагивается.

### Scope and Open Questions

Изменение формализует перечисленные решения из `requirements.md`, включая
семантику ключей, достаточность сертификатного подтверждения владельца, запрет
неизвестного состава цепочки и принятую ответственность сервисов. Контракты
API, точные форматы и правила сравнения ключей, техническая реализация
сертификатной аутентификации, жизненный цикл контейнеров, физическая схема
хранения, способ межсервисного взаимодействия и реализация
конкретных движков RBAC/ABAC/ReBAC в этот предметный scope не входят.

Открытые вопросы сохраняются без выбора поведения по умолчанию:

- Обработка ошибок отдельных правил внутри модели.
- Точный формат и правила сравнения контейнерных ключей, формат и свойства
  ключа субъекта, идентификаторы объектов и моделей доступа.
- Детали сертификатной аутентификации и правила привязки DN к контейнерам.
- Контракты API, жизненный цикл контейнеров и физическая схема хранения.

Нейтральная трактовка неопределённости относится к результату отдельной модели
при установленном полном составе цепочки и не задаёт обработку ошибок отдельных
правил внутри модели. Имя нового репозитория сервиса контейнеров — `container-adm-api`; оно и путь
`/Users/mfedotenko/Projects/Tamarix/container-adm-api` приняты пользователем 2026-10-09.

## Capabilities

### New Capabilities

- `containers` — дерево и типы контейнеров, строковые и составные ключи,
  адресуемый и представляемый контейнеры, общая аутентификация обоих типов
  обращений по сертификату и привязке DN, достаточность этого подтверждения
  для статуса владельца, права владельца и область управления,
  единственный контейнер-держатель и допустимое число моделей, допустимые области ссылок на
  сущности внутри модели.
  Основной путь:
  `openspec/specs/containers/spec.md`; delta:
  `specs/containers/spec.md` внутри этого change.
- `authorization/access-check` — проверка доступа переданного субъекта к объекту
  для действия: положение адресуемого контейнера относительно объекта, выбор
  всех моделей на пути от корня до контейнера объекта, нейтральный результат
  модели для субъекта вне её области, приоритет запрета внутри модели,
  объединение результатов моделей с нейтральной трактовкой неопределённых
  результатов при установленном составе, запрет по умолчанию и запрет при
  неизвестном полном составе цепочки.
  Основной путь:
  `openspec/specs/authorization/access-check/spec.md`; delta:
  `specs/authorization/access-check/spec.md` внутри этого change.

### Modified Capabilities

- `entities/subjects` — добавить требование единственного контейнера-держателя
  субъекта и его сохранения при использовании в модели другого
  контейнера. Основной путь: `openspec/specs/entities/subjects/spec.md`; delta:
  `specs/entities/subjects/spec.md` внутри этого change.
- `entities/objects` — добавить требование единственного контейнера-держателя
  объекта и его сохранения при использовании в модели другого
  контейнера. Основной путь: `openspec/specs/entities/objects/spec.md`; delta:
  `specs/entities/objects/spec.md` внутри этого change.

В существующих спецификациях subjects/objects нет утверждённых требований:
для них будут оформлены `ADDED Requirements`, а не изменения отсутствующих
требований. Связь субъектов и объектов с контейнерами-держателями описывается в соответствующих
entity capabilities. `containers` задаёт допустимые ссылки внутри модели и
общую аутентификацию обращений; `authorization/access-check` использует эти
требования при проверке доступа и описывает вычисление решения. Правила не
дублируются между capabilities. Административные права владельца остаются в
`containers` и не входят в `authorization`.
`access-model` сохраняется как группирующий домен; его новые capabilities этим
change не вводятся.

## Impact

Затронуты `tamarix-specs` (артефакты change и delta specs по четырём путям,
включая новый домен `authorization`) и пять кодовых проектов логического ядра
из карты ниже. Фактическая реализация и проверки на 2026-10-10 — в [tasks.md](tasks.md).
Основные specs будут обновлены при
последующей синхронизации или архивировании изменения.

По проверке локальных кодовых каталогов 2026-10-09 обнаружены только
`openspec/config.yaml`; исходники, контракты, зависимости и DDL не обнаружены.
Предметная ответственность принята пользователем 2026-10-09:

| Сервис / репозиторий | Затронутая область |
| --- | --- |
| `container-adm-api` | Дерево, ключи, привязки DN и отношения контейнеров |
| `entity-subject-adm-api` | Субъекты, их держатели и факты о субъектах; область управления |
| `entity-object-adm-api` | Объекты, их держатели и факты об объектах; область управления |
| `policy-adm-api` | Модели, держатели, ссылки и полный набор моделей; область управления |
| `policy-decision-api` | Сбор полной цепочки и вычисление доступа субъекта |
| `access-assignment-api` | В T-1 не затрагивается |

Административные сервисы проверяют область по фактам дерева сервиса контейнеров
и держателю управляемых данных; `policy-adm-api` получает держателей сущностей
из entity-сервисов. Эта карта не подтверждает реализованные API или хранение.
Технический подход к логическому ядру описан в [design.md](design.md);
его решения приняты в review до зависимой реализации. Локальные контракты
реализованы и проверены; runtime API и хранение требуют отдельных изменений.

Если последующая реализация потребует DDL или Alembic-миграций PostgreSQL,
они относятся исключительно к `db-control`; владение предметными данными и
runtime-доступом этим не определяется. Техническое проектирование API и
хранения потребует отдельных решений до зависимой реализации. Новые
зависимости, конкретные версии и совместимость API этим proposal не задаются.

Для последующих specs нужны явные критерии приёмки основных, негативных и
граничных сценариев; tasks должны связать требования и критерии с
автоматизированными тестами. Принятые уточнения ответственности, допуска и
отказов зафиксированы в постоянном context и [ADR 0001](../../../context/adr/0001-t1-service-boundaries-and-admission.md);
технический подход принят в [ADR 0002](../../../context/adr/0002-t1-logical-core.md).
Рекомендации context не расширяют согласованные требования.
