# T-1. Container definition

Дата: 2026-10-08.
Уточнено: 2026-10-09.

Статус: запись согласованных предметных решений по результатам `openspec-explore`.
Документ служит исходным материалом для последующего оформления требований OpenSpec.

## Контейнеры как держатели сущностей

Контейнеры образуют дерево и содержат объекты, субъекты и модели доступа.

Типы контейнеров в обсуждаемой иерархии:

```text
organization --> environment --> system --> module
```

Любой уровень может отсутствовать. Пропуск уровня не требует создания пустого
контейнера. Корневой контейнер может иметь любой из перечисленных типов.

Порядок типов вдоль пути строго сохраняется. Допустимые связи непосредственного
родителя и ребёнка:

| Тип родителя | Допустимые типы ребёнка |
| --- | --- |
| `organization` | `environment`, `system`, `module` |
| `environment` | `system`, `module` |
| `system` | `module` |
| `module` | Нет |

Обратный порядок типов и повторение типа вдоль одного пути запрещены.
Несколько детей одного типа у общего родителя допустимы: они образуют соседние
ветки и не являются повторением типа вдоль пути.

Каждый объект, субъект и модель доступа имеет ровно одного контейнера-держателя.
Контейнер выступает держателем этих сущностей. Использование сущности в модели
другого контейнера сохраняет её исходного контейнера-держателя.

Владелец контейнера — вызывающий, подтвердивший представляемый контейнер
успешной сертификатной аутентификацией и зарегистрированной привязкой DN.
Этот термин обозначает управляющую сторону;
контейнер-держатель обозначает связь модели, субъекта или объекта с контейнером.

В одном контейнере может находиться `0..N` моделей доступа: ноль, одна или
несколько. Наличие модели в контейнере необязательно.

## Ключи контейнеров

Каждый контейнер имеет свой ключ — текстовую строку.

Составной ключ контейнера задаёт путь от корня дерева до этого контейнера
через ключи контейнеров на пути. Составные ключи контейнеров в Tamarix должны
быть уникальными и однозначно идентифицировать соответствующие контейнеры.
Точный формат составного ключа пока не определён.

## Типы обращений и аутентификация

Обращения к контейнеру бывают двух типов:

| Тип обращения | Назначение |
| --- | --- |
| Проверка доступа | Определить доступ переданного субъекта к объекту для действия по моделям доступа |
| Управление | Управлять моделями доступа, субъектами и объектами в допустимой области контейнеров |

В каждом обращении вызывающий указывает составными ключами два контейнера:

- Адресуемый контейнер `C` — контейнер, к которому направлено обращение.
- Представляемый контейнер `O` — контейнер, от имени которого действует вызывающий.

В обоих типах обращений вызывающий должен пройти аутентификацию по сертификату.
DN сертификата должен быть приписан к представляемому контейнеру `O` в Tamarix.
Указание составного ключа `O` сопровождается подтверждением этого контейнера
через сертификатную аутентификацию.

Успешной сертификатной аутентификации и зарегистрированной привязки DN
сертификата к заявленному `O` достаточно, чтобы признать вызывающего владельцем
`O`; дополнительная административная роль не требуется. Его полные права
управления моделями и сущностями охватывают сам `O` и всех его потомков,
при соблюдении области адресации и предметных инвариантов управления.
При проверке доступа результат для переданного субъекта определяется моделями.

## Область использования сущностей в модели доступа

Для модели с контейнером-держателем `M` допустимы:

| Сущность | Контейнер-держатель сущности |
| --- | --- |
| Субъект | Сам `M` или любой его предок |
| Объект | Сам `M` или любой его потомок |

«Выше» и «ниже» определяются связями предков и потомков конкретного контейнера,
а не сравнением типов контейнеров во всём дереве. Соседние ветки исключены.
Правило действует и при пропущенных уровнях.

Если субъект запроса находится вне допустимой области конкретной модели,
результат этой модели для данного запроса нейтрален. Это правило обработки
запроса сохраняет ограничения на использование сущностей в самой модели.

## Проверка доступа: адресуемый контейнер и цепочка

Обращение для проверки доступа направлено к адресуемому контейнеру `C`, а
вызывающий действует от имени представляемого контейнера `O`, подтверждённого
сертификатом. В обращении передаётся ключ субъекта, доступ которого проверяется.
Держателем проверяемого объекта является контейнер `R`; доступ субъекта определяется
моделями для проверяемых субъекта, объекта и действия.

Адресуемый контейнер `C` должен совпадать с `R` или быть его предком. Это условие
относится к адресуемому контейнеру. Таким образом, `C` находится на пути от корня
дерева до `R`:

```text
root --> ... --> C --> ... --> R
```

Дополнительного ограничения между субъектом запроса и адресуемым контейнером
`C` нет: держателем субъекта не обязан быть `C` или его предок. Допустимость
использования субъекта определяется отдельно для каждой рассматриваемой модели.

Рассматриваются все модели всех существующих контейнеров на пути от корня
дерева до `R`, включая оба конца. В том числе рассматриваются модели предков
адресуемого контейнера `C`.

Если `C` совпадает с `R`, цепочка проверки по-прежнему начинается от корня.
Модели соседних веток в цепочку не входят.

Для каждой рассматриваемой модели сохраняются ограничения использования
субъектов и объектов, описанные выше.

Пример:

```text
organization [model]
  |
  +--> environment [model]
         |
         +--> system C [model, request]
                |
                +--> module R [model, object]
                |
                +--> module X
```

При обращении к `system C` для проверки доступа к объекту в `module R` рассматриваются
модели `organization`, `environment`, `system C` и `module R`.
Ветка `module X` в эту проверку не входит. Представляемый контейнер указывается
отдельно и подтверждается сертификатом.

## Результаты моделей и итог проверки доступа

Следующие правила результатов относятся к обращению для проверки доступа
переданного субъекта.

Определённый результат модели — разрешение, запрет или нейтральный результат.

### Объединение правил внутри модели

Приоритет запрета действует внутри каждой модели:

| Подходящие правила внутри модели | Результат модели |
| --- | --- |
| Есть хотя бы один запрет | Запрет независимо от разрешений остальных подходящих правил |
| Запретов нет и есть хотя бы одно разрешение | Разрешение |
| Подходящих правил нет | Нейтральный результат |

Если модель не содержит подходящего правила для проверяемых субъекта,
объекта и действия, её результат нейтрален. Нейтральный результат не влияет
на решения остальных моделей.

### Неопределённый результат модели

Если результат отдельной модели в цепочке не удалось определить, при
объединении результатов моделей он считается нейтральным. Это относится,
в частности, к ошибке вычисления или недоступности необходимых данных,
которые не позволяют определить результат этой модели.

Неопределённый результат модели не отменяет известное разрешение или запрет
других моделей. Если результаты всех моделей цепочки неопределённы, доступ
запрещён по умолчанию.

Это правило относится к результату отдельной известной модели при установленном
составе цепочки. Обработка ошибок отдельных правил внутри модели остаётся
открытым вопросом.

### Неизвестный состав цепочки

Если невозможно установить полный путь от корня до контейнера-держателя
объекта или полный набор моделей хотя бы одного контейнера этого пути,
результат проверки — доступ запрещён. Известное разрешение доступной части
моделей не изменяет этот результат.

Неизвестный состав цепочки отличается от неопределённого результата
отдельной известной модели. Неполный набор моделей нельзя трактовать как
пустой набор или набор нейтральных результатов.

### Объединение результатов моделей

Следующие правила применяются при установленном полном составе цепочки.

Запрет имеет приоритет над разрешением. Неопределённые результаты считаются
нейтральными при объединении:

| Результаты моделей на цепочке | Итог проверки |
| --- | --- |
| Есть хотя бы один запрет | Доступ запрещён независимо от разрешений остальных моделей |
| Запретов нет и есть хотя бы одно разрешение | Доступ разрешён, в том числе при наличии неопределённых результатов других моделей |
| Разрешений и запретов нет; результаты нейтральные и/или неопределённые | Доступ запрещён по умолчанию |
| Все результаты неопределённые | Доступ запрещён по умолчанию |
| На всём пути от корня до контейнера объекта нет ни одной модели | Доступ запрещён по умолчанию |

## Управление моделями доступа и сущностями

При обращении для управления вызывающий действует как владелец представляемого
контейнера `O`. Его полные права управления охватывают модели доступа, субъекты
и объекты самого `O` и всех его потомков.

Адресуемый контейнер `C` должен совпадать с `O` или быть его потомком. Владелец
`O` может адресовать управление непосредственно к потомку, пользуясь своими
полными правами над потомками. Обращение для управления к предку `O` или в
соседнюю ветку недопустимо.

Через адресуемый контейнер `C` можно управлять только моделями и сущностями,
держателями которых являются сам `C` или его потомки. Если контейнер-держатель управляемой
модели или сущности обозначен `D`, действуют оба условия:

- `C` совпадает с `O` или является потомком `O`.
- `D` совпадает с `C` или является потомком `C`.

| Адресуемый контейнер относительно представляемого `O` | Обращение для управления |
| --- | --- |
| Сам `O` | Допустимо; область управления — `O` и его потомки |
| Потомок `O` | Допустимо; область управления — адресуемый контейнер и его потомки |
| Предок `O` | Недопустимо, в том числе для управления данными самого `O` |
| Соседняя ветка | Недопустимо |

Например, моделями и сущностями `D`, являющегося потомком `O`, владелец `O`
может управлять через обращение к `O` или к `D`. Владелец самого `D` может
управлять данными, содержащимися в `D`, через обращение к `D`, но не через обращение к предку
`O`.

При управлении сохраняются единственный контейнер-держатель каждой сущности
или модели и ограничения использования сущностей внутри модели.

## Распределение требований по доменам и capabilities

Домен `authorization` охватывает только проверку доступа субъектов. Для неё
выделяется capability `authorization/access-check`. Управление моделями доступа
и сущностями относится к `containers`.

| Capability | Ответственность |
| --- | --- |
| `containers` | Дерево и типы контейнеров, строковые и составные ключи, адресуемый и представляемый контейнеры, общая аутентификация обращений по сертификату, права владельца на управление, единственный контейнер-держатель и количество моделей, допустимые области ссылок на сущности в модели |
| `authorization/access-check` | Обращение для проверки доступа переданного субъекта, положение адресуемого контейнера относительно объекта, выбор цепочки моделей, проверка применимости модели к субъекту, объединение правил внутри модели и результатов моделей, нейтральная трактовка неопределённого результата модели и запрет по умолчанию |
| `entities/subjects` | Единственный контейнер-держатель субъекта и его сохранение при использовании субъекта в модели другого контейнера |
| `entities/objects` | Единственный контейнер-держатель объекта и его сохранение при использовании объекта в модели другого контейнера |

`authorization/access-check` использует общие требования аутентификации из
`containers`. Ограничения на допустимые ссылки внутри модели задаются в
`containers`; нейтральный результат модели для субъекта вне её области
описывается в `authorization/access-check` как правило обработки запроса.

`access-model` остаётся группирующим доменом. Новые дочерние capabilities этого
домена в рамках текущего изменения не вводятся.

## Распределение ответственности между сервисами

Принято пользователем 2026-10-09. Эта карта задаёт предметную ответственность,
а не транспорт взаимодействия, физическое хранение или подтверждённую реализацию.

| Сервис / репозиторий | Ответственность в T-1 |
| --- | --- |
| `container-adm-api` | Дерево, типы, ключи и зарегистрированные привязки DN; сведения об отношениях контейнеров |
| `entity-subject-adm-api` | Субъекты, их единственные держатели и факты о субъектах |
| `entity-object-adm-api` | Объекты, их единственные держатели и факты об объектах |
| `policy-adm-api` | Модели, их единственные держатели, ссылки на сущности и полный набор моделей заданных контейнеров |
| `policy-decision-api` | Сбор полной цепочки моделей и вычисление доступа субъекта |
| `db-control` | Все DDL и Alembic-миграции PostgreSQL |
| `access-assignment-api` | В T-1 не затрагивается |

Административные сервисы проверяют область управления по данным сервиса
контейнеров и держателю управляемых данных. `policy-adm-api` использует факты
entity-сервисов для проверки областей ссылок. Владение DDL в `db-control`
не определяет физическое размещение предметных данных или runtime-доступ к ним.

## Вопросы, оставшиеся открытыми

После уточнения предметных решений остаются открытыми:

- Обработка ошибок отдельных правил внутри модели.
- Точный формат и правила сравнения контейнерных ключей, формат и свойства
  ключа субъекта, идентификаторы объектов и моделей доступа.
- Детали сертификатной аутентификации и правила привязки DN к контейнерам.
- Контракты API, жизненный цикл контейнеров и физическая схема хранения.
