# Design

## Context

Мотивация — в [proposal.md](proposal.md). Принятый процесс — в
[testing.md](../../../context/testing.md) и
[ADR 0004](../../../context/adr/0004-testing-regression-lifecycle.md).
Этот change оформляет процесс и план его реализации; создание отдельной
тестовой репы и исполняемого gate остаётся открытой работой.

Прочитаны context README, architecture-principles, technology-stack,
service-architecture, data-architecture, api-guidelines, security, patterns,
реестр ADR и ADR 0003/0004. Store-only, Python/uv/pytest логического ядра и
владение DDL в `db-control` приняты ранее. Новые pins тестовой репы этим
планом не выбираются: их совместимость проверяется при подготовке среды.

Исследованы контрактные тесты `policy-decision-api`, CD runtime/verify/CI
и AGENTS/config обоих репозиториев. Межсервисные ядра проверяются в памяти,
HTTP runtime объявляет только `/health`. `TamarixTests`, его registry/runner
и CI archive gate отсутствуют. CD instructions обновлены для координации,
но pipeline ещё не вызывает отдельную тестовую репу.

OpenSpec 1.14.1 поддерживает `skip_specs: true` и operation guidance.
Change не меняет предметное поведение; артефакт specs пропускается явно.
Generated skills не редактируются, существующая `spec-driven` схема сохраняется.

## Goals / Non-Goals

**Goals:**

- Один постоянный межсервисный набор с проверяемой связью критериев и тестов.
- Явный отбор candidate/regression и воспроизводимые результаты для archive.
- Проверка исполнения условий вне advisory-инструкций OpenSpec.
- Сохранение принятых границ: тесты в TamarixTests, предметное планирование
  и archive в store, orchestration и CD planning локально в TamarixCD.

**Non-Goals:**

- Бизнес endpoints, PKI, storage adapters, новая БД-топология и миграции.
- Перенос CD tests или переписывание исторических архивов T-1.
- Создание custom schema или обновление pins существующих сервисов.
- Объявление недоступного предметного e2e выполненным через health/in-memory тест.

## Decisions

### Реестр и постоянные исходники

`TamarixTests/registry.yaml` задаёт уникальный стабильный ID каждого тестового
случая, русское `description`, `level`, `state`, `introduced_by`, точный node ID и список связей
со spec/Requirement/Scenario/критерием. Коллекция проверяет существование
node ID, включая параметризованный случай. Runner читает реестр как единый
источник отбора и формирует отчёт по этим же ID; дублирующие regression markers
не вводятся. Перенос исходников отвергнут из-за смены путей и риска копий.

Все тесты проекта имеют русское описание того, что проверяется, при каких
условиях, какой результат ожидается и для чего применяется проверка.
Для Python это docstring функции/метода; параметризованные случаи получают
понятные русские пояснения. Внешний registry и отчёты показывают то же
назначение без чтения кода. Валидатор отвергает отсутствие/пустое описание,
а содержательность и соответствие фактическому поведению проверяются review;
одного наличия кириллицы недостаточно. Правило распространяется на сервисные
unit/component, CD/smoke и инфраструктурные тесты; оно не требует перевода
технических идентификаторов и не означает, что прежние тесты уже исправлены.

Runner выбирает candidate текущего change и весь актуальный regression.
Если MODIFIED/REMOVED меняет старую проверку, её согласованное обновление
или retirement является частью change и проверяется вместе с новым набором;
невозможно молча исключить падающий тест из регресса.
Skip/xfail обязательного случая не засчитывается как успех. Пустой первый
регресс допустим как явно отмеченный bootstrap, но обязательный новый набор
не может быть пустым. Tooling-only change не требует выдуманных предметных тестов.

### Контракт среды и результатов

Runner инициируется требованием пользователя, ручным CI job или уже
согласованной задачей проверки; повторного подтверждения не требуется.
Выбор test ID/change/уровня/всего регресса и повторный запуск доступны
независимо от archive, включая регресс без активного change. Без отдельного
запроса новые фоновые/периодические и commit/start/archive триггеры не добавляются.

Gate/runner принимают manifest с фиксированными commits сервисов, CD и tests,
исходной revision store и hashes проверенных specs/deltas, image digests,
состоянием миграций, адресами сервисов и идентификатором изоляции данных.
Неприменимые образы/миграции имеют явное значение отсутствия.
Точные поля/версия JSON manifest и runner CLI согласуются в локальном CD change
до интеграции; они не определяют предметные URL или wire-поля.

Результат содержит run ID, timestamps, команды, выбранные/собранные test ID
и node ID, итоги каждого случая, manifest/hash и ссылки/hash CI-артефактов.
Для каждого внешнего случая выводится русское описание его проверки и назначения.

Каждый прогон создаёт новый `reports/<run-id>/` в заданном output-dir:
обязательные summary.md на русском и results.json, JUnit XML по требованиям
CI. Отчёт связывает запрошенный, собранный и выполненный наборы, общие счётчики
и итоги каждого случая, timestamps/duration, ошибки и артефакты. Отчёт по
выборочному набору не подходит для archive, даже если выбранные случаи прошли.
Отчёт сохраняется и при fail/ошибке коллекции или среды/отмене; NOT_RUN
отличается от SKIP. Начальный снимок записывается до выполнения тестов,
результаты обновляются по мере исполнения. Обычная отмена завершает отчёт
как CANCELLED; при принудительном завершении остаётся неполный снимок,
который gate отклоняет. Прежние отчёты не перезаписываются.
Gate сопоставляет результат с входными revisions и целевыми критериями,
а не доверяет exit code или произвольному verification.md отдельно от отчёта.
Тестовые секреты не включаются в отчёты. Источник тестовых данных и очистка
выбираются по публичным контрактам и владению миграциями, без чужого DDL.

### Promotion и archive

Проектная обёртка в store сначала проверяет связи/коллекцию и результаты,
проверяет зафиксированный promotion в тестовой репе, затем вызывает OpenSpec
archive без отключения validation. Окончательный tests commit после promotion
должен иметь свой успешный прогон; отчёт до изменения registry недостаточен.
До первого изменения основных specs или перемещения change все условия
проверяются; прямое archive дополнительно контролируется обязательным CI
центрального store. Привязка required check к merge настраивается в выбранной
CI-платформе, а не только наличием YAML файла.

Обёртка/CI gate потребляет предоставленный отчёт, не инициируя отсутствующие
тесты. Нет/устарел/неполон отчёт — отказ с указанием необходимого явного прогона
и сохранением активного change. Прогон перед archive может входить в тот же
явный запрос; диагностический выборочный отчёт не заменяет обязательный набор.

Межрепозиторной атомарности нет. Операция сохраняет ID, revisions и шаги
promotion/archive. Повторный запуск сверяет вход, продолжает достигнутое
состояние и не создаёт второй promotion/archive. Новый вход требует нового
прогона. После promotion без archive change остаётся активным; evidence
фиксирует частичный успех. Проверка итоговых specs использует входные hashes
и результат delta merge, не требует невозможного совпадения итогового store
commit с входным commit прогона.

### Поэтапное внедрение и границы планирования

Сначала добавляются правила/ADR и план. Затем создаётся TamarixTests,
registry/runner и проверки их отказов. CD предоставляет среду и внешний
прогон в собственном локальном change. Этот центральный change отслеживает
получение согласованного CD контракта и его evidence, но не содержит задач
изменения CD runtime/CI. После этого внедряется wrapper/required check store.
До появления инструментов действует явная ручная проверка агентом.

## Risks / Trade-offs

- [Инструкции ошибочно принимаются за gate] → обозначить отсутствие
  реализации и проверить отказ прямого архивирования в обязательном CI.
- [Ложный PASS или устаревший отчёт] → сверять collection, каждый обязательный
  случай, manifest и immutable revisions; пустой/пропущенный набор отклонять.
- [Promotion зафиксирован, archive отказал] → сохранять состояние и проверять
  повтор без дублирования; change остаётся активным до завершения.
- [Неполный runtime] → фиксировать реальные границы и оставлять HTTP e2e
  открытым до соответствующих endpoints/adapters.
- [Дрейф связей при rename/remove] → валидировать реестр относительно целевых
  specs и требовать согласованную историю обновления/retirement.

## Migration Plan

Правила и принятый процесс добавляются без изменения основных specs или
исторических архивов. Начальный registry заполняется только существующими
проверенными случаями через явные задачи; готовность ядра не переименовывается
в HTTP e2e. Создание бизнес сценариев следует соответствующим предметным changes.

Документация откатывается через Git с сохранением записи решения. Откат
автоматизации сохраняет registry/evidence; до восстановления gate условия
archive проверяются явно. Изменение политики требует нового принятого решения.

## Open Questions

Remote/checkout TamarixTests, совместимые pins его среды, версия контракта
CD manifest/runner, CI-платформа и хранилище отчётов фиксируются задачами
внедрения до зависимых интеграций. Бизнес API/PKI/storage выбираются отдельными
предметными changes; этот план не зависит от выдуманных endpoints.
