## Планируемые команды проверки

Команды ниже запускаются при реализации согласованной проверки, а не при
подготовке этого proposal. `MANIFEST` и `REPORT` заменяются абсолютными путями
к реальным файлам; секреты передаются существующим механизмом среды.

Из `db-control`:

```sh
.venv/bin/python tools/run_tests.py --output-dir reports -- tests/component/test_attribute_shapes.py tests/component/test_attributes_schema.py tests/component/test_attribute_equality.py tests/component/test_database_roles.py tests/component/test_dn_codec.py tests/component/test_migrations.py -q
```

Из `TamarixTests`:

```sh
.venv/bin/python -m tamarix_tests validate-registry --store ../Tamarix/tamarix-specs --change t-5-persistant-change-1
.venv/bin/python -m tamarix_tests run --store ../Tamarix/tamarix-specs --manifest MANIFEST --change t-5-persistant-change-1 --output-dir reports --junit
.venv/bin/python -m tamarix_tests promote --store ../Tamarix/tamarix-specs --change t-5-persistant-change-1 --report REPORT
```

После promotion использовать новый manifest и повторить полный --change run.
Отдельный `--regression` run не нужен, если тот же набор уже включён в --change
и новых изменений после проверки нет. Диагностический --id/--level не заменяет
полный допуск archive.

Из `tamarix-specs`:

```sh
openspec validate t-5-persistant-change-1 --strict --store tamarix-specs
python3 tools/docs_check.py check
python3 tools/docs_check.py prepare --change t-5-persistant-change-1 --base-ref BASE_SHA
python3 tools/docs_check.py review --change t-5-persistant-change-1
python3 tools/archive_gate.py check --tests ../../TamarixTests --change t-5-persistant-change-1 --report REPORT
```

BASE_SHA — сохранённый baseline до собственных docs changes. После изменения
исходных change/docs evidence обновляется через prepare --refresh и новый review;
archive gate использует уже готовый отчёт и не запускает тесты сам.


## Прослеживаемость требований и критериев приёмки

Это план автоматизированных проверок для реализации; он не является evidence и не подтверждает наличие новых функций, коллекцию либо PASS. Существующие IDs/node IDs прочитаны из текущего `TamarixTests/registry.yaml`; новые ссылки ниже планируемые.

Полный путь delta spec для **каждой** строки таблицы: `openspec/changes/t-5-persistant-change-1/specs/attributes/spec.md`. Для `registry.links.spec` использовать постоянный путь `openspec/specs/attributes/spec.md`; `validate-registry --change t-5-persistant-change-1` разрешает будущие Requirement/Scenario через эту delta.

Корни репозиториев: `TamarixTests` и `db-control` из project context. Приведены полные pytest node IDs относительно соответствующего корня, без сокращений путей. Component runner db-control использует точный node ID также как test ID; отдельный integration registry ID для component tests не вводится.

Новые `persistent-shapes-c01`–`persistent-shapes-c13`: `level: integration`, `state: candidate`, `introduced_by: t-5-persistant-change-1`, постоянный файл `tests/integration/persistence/test_shapes.py`. Если один cNN связан с несколькими сценариями, он должен явно проверять **каждый** WHEN/THEN соответствующих строк, а не только общий happy path. Для каждого случая нужны русские docstring/DESCRIPTIONS и registry description.

Существующие regression IDs сохраняют идентичность. Для `persistent-attributes-c17/c18` обновить проверку на перепривязку shape и точный прежний shape_id, сохранив empty set/tombstone смысл; совместимые wrappers также остаются проверяемыми. Во всех изменённых случаях заново сверить русские описания и links с итоговой delta.

### Границы и дополнительные обязательные задачи проверки

- Component-only строки проверяют реальные декларативные ограничения, whole-row guard либо миграции; публичная routine может отвергнуть вход раньше FK/CHECK и поэтому сама не доказывает эти свойства. Новые component functions с `all_owner_families` явно проходят container/subject/object/model внутри теста; при переходе к pytest parameterization перед завершением заменить ссылки точными собранными node IDs каждого параметра.
- c03 дополнительно проверяет обе очередности applicability ↔ rebind при общей definition row lock; c10 — обе очередности instance-create ↔ rebind через реальные независимые транзакции. Проверять итоговые строки и отсутствие частичного состояния, не ограничиваться кодом ошибки.
- c12 вызывает контролируемый 40001 и доказывает повтор всей transaction, повторное получение фактов и сохранение исходного expected_revision; старый container c24 сохраняет реальную конкуренцию, но один недетерминированный race не доказывает каждый внутренний шаг retry.
- c13 проверяет прежние SQL catalog signatures, no-op wrapper при равной tuple, атомарный отказ без orphan shape, прежние имена/порядок/типы/collation колонок fact views и новые shape_facts/definition_shape_facts. Широкий старый регресс остаётся дополнительным consumer coverage.
- Populated migration test принадлежит db-control: Alembic API upgrade до `20261015_0003`, заполнение именно прежней схемы, точные до/после fingerprints всех четырёх семейств, ID/keys/applicability/revisions/mutation_version/DN bytes и keys/views/ACL, затем upgrade head и повторный upgrade. TamarixTests fixture всегда ставит head и эту проверку не заменяет; DDL в TamarixTests не добавлять.
- Дополнительный design rollback, не отдельный Scenario текущей delta: db-control `tests/component/test_migrations.py::test_shapes_disposable_downgrade_restores_previous_contract` и `tests/component/test_migrations.py::test_shapes_downgrade_without_disposable_safeguard_preserves_state`. Проверить восстановление 0003, документированную потерю shape ID/key/sharing, отказ без safeguard до мутаций; обновить существующий DN downgrade test, который целится в 0002.
- До реализации тестов учитывать actual SQL wrappers/views из design; не вводить tests regex/length/range и автоматический semantic dedup. Разные ключи с одинаковой текущей семантикой допустимы; c04/c08/c09 должны сохранять точную идентичность форм.
