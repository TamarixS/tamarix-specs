# Архитектурные принципы и SDD

Статусы — в [README](README.md). Здесь отдельно описаны установленные правила
работы с OpenSpec и рекомендации по проектированию, которые ещё не являются
утверждённой архитектурой сервисов.

## Установленные правила SDD

Источники: [существующий config](../config.yaml) и текущие решения пользователя.

1. Один store `tamarix-specs` содержит specs, changes и постоянный context.
   Кодовые каталоги сохраняют только указатель `store: tamarix-specs` внутри
   OpenSpec; не создавать там локальные specs/changes.
2. Specs описывают поведение capabilities, а не структуру сервисов. Полные пути:
   `entities/subjects`, `entities/objects`, `containers`; T-1 добавляет
   `authorization/access-check` для проверки доступа субъектов.
   `access-model` пока группирует будущие capabilities, без утверждённого второго уровня.
3. Заготовки subjects/objects не содержат утверждённых требований. Нельзя
   изобретать поведение для их заполнения, создавать spec.md или capabilities
   без согласованного изменения.
4. Proposal описывает проблему, цель, границы, полные пути capabilities,
   затронутые репозитории и открытые вопросы.
5. Specs используют структурные заголовки OpenSpec `### Requirement:` и
   `#### Scenario:`, нормативные SHALL/MUST и WHEN/THEN. Delta specs сохраняют
   путь capability и разделы ADDED/MODIFIED/REMOVED/RENAMED Requirements.
6. Design объясняет решения, альтернативы, распределение ответственности,
   контракты и совместимость; изменения данных включают миграции и откат.
7. Tasks содержат нумерованные разделы и чекбоксы `- [ ]`; у каждой задачи
   указан репозиторий, проверяемый результат и порядок зависимостей. Один
   центральный tasks.md не делится автоматически по кодовым репозиториям.
8. Пояснения пишутся по-русски; имена сервисов, пути, структурные заголовки и
   SHALL/MUST сохраняются. Факты, рекомендации и TBD обозначаются явно.
9. Уже принятые решения сохраняются. Новое архитектурное решение не следует
   из имени сервиса, типового стека или текста рекомендации.
10. По решению пользователя от 2026-10-14 предметные integration/e2e тесты
    принадлежат `TamarixTests`, связанному с центральным store. Их включение
    в регресс и проверки перед archive определены в [testing.md](testing.md)
    и [ADR 0004](adr/0004-testing-regression-lifecycle.md). Принятие процесса
    отделено от реализации runner/CI gate; CD planning остаётся в `TamarixCD`.

## Практический цикл работы

Перед design/tasks агент явно читает [README](README.md), [стек](technology-stack.md),
[границы сервисов](service-architecture.md), этот документ и
[реестр ADR](adr/README.md). Для данных добавляет [data](data-architecture.md),
для контрактов — [API](api-guidelines.md), для авторизации и доверия —
[security](security.md), для выбора паттернов — [patterns](patterns.md).
Для design/tasks, тестов и предметного archive явно читает [testing](testing.md).

Далее читает соответствующие основные specs целиком и текущий change; проверяет
доступный код и зависимости затронутых репозиториев. В design указывает источники,
статусы решений и нерешённые вопросы. Если зависимое решение TBD, допустимо
оформить альтернативы и задачу принятия решения; нельзя выдавать выбранную
догадку за факт. Перед реализацией задачи, зависящие от такого решения, требуют
его явного согласования.

OpenSpec передаёт строку context и artifact rules из config в инструкции.
Это не загрузка Markdown-файлов по ссылкам. [AGENTS.md](../../AGENTS.md) дополняет
правила для агентов, которые читают этот формат; запускающему агенту нужно
иметь доступ к store и явно выполнить чтение.

## Рекомендации по проектированию

| Принцип | Что показать в design/review | Что пока TBD |
|---|---|---|
| Явные границы | Ответственный за операции и факты, публичный контракт; избегать связи через внутренние классы другого сервиса | Механизм интеграции и границы вне принятой карты T-1 |
| Минимальная сложность | Паттерн решает конкретную проблему; сравнить простой вариант | Hexagonal/Clean Architecture, DDD и другие паттерны |
| Совместимость | Потребители, старый/новый контракт, переходный период и порядок внедрения | Политика версий API/контрактов и поддерживаемое окно |
| Целостность данных | Инварианты, транзакционные границы, конкуренция, ошибки и восстановление | Уровни консистентности и распределение хранилищ |
| Безопасность | Границы доверия, защита администрирования, ошибочные и отказные сценарии | Конкретная PKI/доверие и fail policy вне принятой семантики T-1 |
| Надёжность | Таймауты, ограничение нагрузки, стратегия повторов и отзыва доступа | SLO, численные бюджеты, HA |
| Проверяемость | Сценарий из specs связан с задачей и проверкой результата | Runtime-интеграционная инфраструктура; pytest для ядра T-1 принят в ADR 0003 |
| Наблюдаемость | Как обнаружить ошибку и объяснить решение без раскрытия секретов | Метрики, логи, трассы, сроки хранения |

Ни одна строка этой таблицы не выбирает библиотеку, транспорт или схему БД.

## Review и принятие решений

Правила сохранения store-only и достоверности выше обязательны для работы с
контекстом. Следующий checklist рекомендуется как содержание архитектурного review;
команда ещё не определила роли утверждающих и автоматические CI-gates.

- Scope и сценарии соответствуют proposal; новые возможности не маскируются
  как «техническая правка контекста».
- Каждое существенное решение имеет статус, источник, альтернативы и последствия.
- Для границ/данных/контрактов проверены все затронутые сервисы, совместимость,
  порядок внедрения и путь восстановления.
- Для авторизации рассмотрены отказ, устаревшие данные, отзыв доступа, аудит
  и административные операции.
- Tasks связывают требования с реализацией и проверками; не объявлять выполненным
  то, для чего есть только описание.
- Архитектурные изменения отражены в [ADR](adr/README.md) и в context;
  ссылки доступны, устаревшее решение помечено заменённым, история сохранена.
