# Постоянный контекст Tamarix

Этот каталог хранит архитектурно-технологический контекст для централизованной
SDD-разработки Tamarix. Он помогает проектировать изменения, но не заменяет
требования capabilities в `openspec/specs/` и артефакты `openspec/changes/`.

## Актуальное руководство продукта

Начинать знакомство с продуктом нужно с [`docs/README.md`](../../docs/README.md).
В docs описаны текущие T-1/T-3 сервисы, Python/HTTP границы, PostgreSQL,
эксплуатация и разработка с Mermaid-схемами. Этот context сохраняет историю
решений и рекомендации; датированные наблюдения ниже не означают отсутствия
позднейшей реализации. В T-3 добавлены `attributes` и `access-model/models`,
постоянное хранение и transactional adapters; факты — в
[архиве T-3](../changes/archive/2026-10-15-t-3-persistent/README.md) и docs.

По запросу пользователя от 2026-10-15 docs обновляются до каждого нового archive.
Процесс: [development](../../docs/development.md),
[исполняемый gate](../../tools/ARCHIVE_GATE.md).

## Статусы сведений

| Статус | Как использовать |
|---|---|
| Установлено | Прямое решение пользователя или подтверждение в существующих файлах; указан источник |
| Рекомендация | Предложение для design/review; само по себе не утверждает архитектуру или поведение |
| TBD | Решение или подтверждение отсутствует; требуется уточнение в change и, при архитектурном выборе, ADR |

Наличие технологии в примере или её распространённость не меняет статус.
Наблюдение в локальной среде не означает закреплённую зависимость проекта.
Для принятия рекомендации нужен явный результат review; см. [реестр ADR](adr/README.md).

## Установленные факты

- Проект расположен в `~/Projects/Tamarix`, центральный репозиторий — `tamarix-specs`.
- Выбран OpenSpec Store beta, вариант A (store-only): specs, changes и общий
  контекст находятся в `tamarix-specs`. Кодовые каталоги содержат указатели
  `store: tamarix-specs`, без собственных specs и changes.
- Идентификатор store: `tamarix-specs`; источник — [.openspec-store/store.yaml](../../.openspec-store/store.yaml).
- Схема workflow: `spec-driven`; существующие пользовательские правила —
  [openspec/config.yaml](../config.yaml).
- Пользователь 2026-10-14 принял добавление процесса отдельных integration/e2e
  тестов в `TamarixTests` и их включения в регресс перед архивированием.
  Размещение, traceability, evidence и границы CD определены в
  [testing.md](testing.md) и [ADR 0004](adr/0004-testing-regression-lifecycle.md).
  Реализованные runner/registry и archive gate описаны в testing.md;
  фактические прогоны и required CI policy подтверждаются evidence T-2.
- Предметная область — авторизация и модели RBAC, ABAC, ReBAC. Это направление
  продукта, а не подтверждение уже реализованной поддержки всех моделей.
- Утверждённый стек: Python, PostgreSQL, FastAPI для REST API, Pydantic,
  SQLAlchemy, Psycopg 3, Alembic и uv. Для всех — latest stable; Python без
  prerelease. Источник — решения пользователя, подтверждённые 2026-10-08;
  официальные источники и оставшиеся TBD — в [technology-stack.md](technology-stack.md).
- Для пяти проектов логического ядра T-1 2026-10-09 отдельно приняты Python
  3.15.0 final, uv/uv_build 0.12.24, pytest 9.1.1 и устанавливаемые `src/` пакеты.
  Локальные `facts.py / ports.py / core.py` используют различимые complete/unknown
  и не требуют общего runtime-пакета. Источник — прямые ответы пользователя
  «Да, принять среду», «Да, принять интерфейсы» в
  [ADR 0003](adr/0003-t1-python-environment-and-contracts.md).
  На 2026-10-10 установка, lock-файлы, сборка и тесты пяти проектов подтверждены;
  результаты и границы — в [evidence T-1](../changes/archive/2026-10-13-t-1-container-definition/tasks.md#результаты-проверок).
- Базовые версии согласуются между сервисами. Проект и зависимости описываются
  в `pyproject.toml`, PyPI-зависимости фиксируются в `uv.lock`, версия Python —
  в `.python-version`; воспроизводимая установка — `uv sync --frozen` после
  проверки `uv lock --check`. Обновления — после проверки совместимости и тестов;
  PostgreSQL major upgrade и миграции оцениваются отдельно.
- Репозиторий `db-control` — единственный владелец DDL и Alembic-миграций
  PostgreSQL; остальные сервисы не создают собственных миграций и не управляют
  схемой самостоятельно. Это не определяет владельцев предметных данных,
  топологию БД или runtime-доступ.
- AuthZEN рассматривается как стандарт взаимодействия авторизации; его принятие
  и профиль совместимости пока не определены.
- Состав доступных кодовых каталогов: `db-control`, `entity-subject-adm-api`,
  `entity-object-adm-api`, `policy-adm-api`, `policy-decision-api`,
  `access-assignment-api`. В T-1 пользователь принял отдельный сервис контейнеров
  и карту предметной ответственности. В review 1.6/2.1 принято имя
  `container-adm-api` и путь `/Users/mfedotenko/Projects/Tamarix/container-adm-api`;
  репозиторий подготовлен с [store pointer](../../../container-adm-api/openspec/config.yaml).
  Технический подход логического ядра принят в [ADR 0002](adr/0002-t1-logical-core.md).
  Источник — ответы пользователя 2026-10-09 в
  [ADR 0001](adr/0001-t1-service-boundaries-and-admission.md), карта —
  [service-architecture.md](service-architecture.md). Логические ядра пяти сервисов
  реализованы и проверены; runtime-адаптеры требуют отдельных изменений.
- В T-1 успешная сертификатная аутентификация и DN, зарегистрированный к
  заявленному `O`, достаточны для статуса владельца. Управление моделями и
  сущностями ограничено `O ≼ C ≼ D` и предметными инвариантами; доступ
  переданного субъекта определяется отдельно по моделям.
- В T-1 неизвестный полный путь до держателя объекта или полный набор моделей
  даёт запрет даже при известном разрешении. Неопределённость отдельной известной
  модели при установленном составе нейтральна; разрешение + неопределённость
  без запрета дают разрешение. Источник и границы — ADR 0001 и
  [security.md](security.md).

Срез проверки, повторённый 2026-10-09: в шести кодовых каталогах найдены только
`openspec/config.yaml` с `store: tamarix-specs` и служебные `.DS_Store`.
Исходники, зависимости, контракты, DDL и миграции не обнаружены локально;
это не устанавливает состояние внешней runtime-системы. До подготовки context
2026-10-08 отдельных ADR не было; 2026-10-09 зарегистрированы ADR 0001–0003.
При закрытии задачи 2.1 новый Git-репозиторий `container-adm-api` содержал
только store pointer. К 2026-10-10 в пяти проектах созданы логические ядра,
локальные контракты и тесты. Актуальное состояние и прослеживаемость — в

| `entities/objects` | Capability объектов | Основная [спецификация](../specs/entities/objects/spec.md) содержит требования к держателю; [delta T-1](../changes/archive/2026-10-13-t-1-container-definition/specs/entities/objects/spec.md) сохранена в архиве |
| `containers` | Capability без второго уровня | Основная [спецификация](../specs/containers/spec.md) содержит принятую семантику T-1; [delta T-1](../changes/archive/2026-10-13-t-1-container-definition/specs/containers/spec.md) сохранена в архиве |
| `authorization/access-check` | Проверка доступа переданного субъекта | Основная [спецификация](../specs/authorization/access-check/spec.md) содержит принятую семантику T-1; [delta T-1](../changes/archive/2026-10-13-t-1-container-definition/specs/authorization/access-check/spec.md) сохранена в архиве |
| `attributes` | Общие типизированные атрибуты | [Спецификация T-3](../specs/attributes/spec.md) |
| `access-model/models` | Постоянная идентичность и metadata моделей | [Спецификация T-3](../specs/access-model/models/spec.md); access-model остаётся группирующим доменом |

Не создавать `spec.md` или новые capabilities для заполнения дерева. Для
`containers` не требуется выдумывать второй уровень. Новые требования и
расширение структуры вводятся только в рамках согласованного change.
Сервисы и capabilities — разные оси: одна capability может затрагивать несколько
кодовых репозиториев; это не повод переименовывать её в имя сервиса.

## Общий словарь

Это понятия предметной области, а не выбранная физическая модель.

| Понятие | Рабочее значение для обсуждения |
|---|---|
| Субъект / subject | Тот, для кого проверяют возможность выполнить действие |
| Объект / object, resource | Защищаемый ресурс; точное соответствие object и AuthZEN resource — TBD |
| Действие / action | Операция, право на которую проверяют; каталог действий — TBD |
| Политика / policy | Правило принятия решения; язык и ошибки отдельных правил — TBD; приоритет запрета внутри модели и в цепочке принят в T-1 |
| Назначение / assignment | Предоставление роли или доступа; точные виды и жизненный цикл — TBD |
| Атрибут | Характеристика субъекта, объекта либо контекста, используемая в ABAC |
| Отношение / relationship | Типизированная связь, используемая в ReBAC; направления и ограничения — TBD |
| Container | Узел типизированного дерева, идентифицируемый составным ключом; предметная семантика принята в T-1, физическое представление и lifecycle — TBD |
| Контейнер-держатель | Единственный контейнер субъекта, объекта или модели; ссылка модели другого контейнера его не меняет |
| Владелец контейнера | Вызывающий, подтвердивший `O` сертификатом и зарегистрированной привязкой DN; имеет права управления в согласованной области |
| RBAC / ABAC / ReBAC | Контроль доступа на основе ролей / атрибутов / отношений; сочетание моделей — TBD |

Понятия PEP/PDP/PAP/PIP определены в [security.md](security.md); они не задают
автоматически отдельные сервисы или выбранный движок авторизации.

загрузку агентских инструкций из соседнего репозитория.
