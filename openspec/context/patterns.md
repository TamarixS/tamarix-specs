# Паттерны и критерии их применения

Этот документ помогает обосновывать решения в design и на review. Он не назначает Tamarix
конкретный фреймворк, стиль архитектуры или способ хранения данных.
Обозначения статусов и карта документов: [README](README.md).

## Установленные факты

- Постоянный контекст и спецификации централизованы в репозитории `tamarix-specs`.
- Кодовые репозитории используют `store: tamarix-specs`; применяется вариант A, store-only.
- Capabilities T-1: `entities/subjects`, `entities/objects`, `containers`,
  `authorization/access-check`; `containers` без второго уровня.
- `access-model` пока служит только группирующим доменом.
- Предметная область включает RBAC, ABAC, ReBAC и авторизацию.
- В [ADR 0001](adr/0001-t1-service-boundaries-and-admission.md) приняты границы
  T-1, достаточность сертификата + DN и запрет при неизвестном полном составе
  цепочки. Неопределённая известная модель при установленном составе нейтральна.
  Это не подтверждает реализацию технических алгоритмов.
- В [ADR 0002](adr/0002-t1-logical-core.md) отдельно принят технический подход T-1:
  структурные отношения, проверки до изменения, полная сборка цепочки,
  независимые операторы и логические интерфейсы поставщиков фактов.
- В [ADR 0003](adr/0003-t1-python-environment-and-contracts.md) приняты для
  T-1 локальные `facts.py / ports.py / core.py`, Protocol и различимые
  complete/unknown-результаты без общего runtime-пакета. Testing — pytest 9.1.1,
  именованные случаи сценариев/таблиц; упаковка — `src/` pure-Python с uv_build.
  Фактические lock/install/build/test пяти проектов подтверждены на 2026-10-10
  в [evidence T-1](../changes/archive/2026-10-13-t-1-container-definition/tasks.md#результаты-проверок).
- В прочитанных материалах нет утвержденных решений о DDD, Hexagonal Architecture,
  CQRS, event sourcing или outbox. SQLAlchemy и остальной
  [технологический стек](technology-stack.md) утверждены отдельно и не выбирают
  эти архитектурные паттерны.

## Рекомендации: выбирать паттерн по задаче

Строки ниже — кандидаты для обсуждения. Наличие строки не означает принятие паттерна.
Design должен назвать проблему, альтернативы, стоимость и критерий проверки.

| Кандидат | Когда рассматривать | Что проверить до принятия |
| --- | --- | --- |
| Отделение правил доступа от транспорта | Правила нужны в нескольких API или исполнениях | Можно ли тестировать правило без HTTP/БД; не дублируется ли доменная логика |
| Явные границы модулей | Общий код создает неявную связанность сервисов | Какие зависимости допустимы; кто выпускает и поддерживает общий контракт |
| Версионирование модели и политики | Решение должно быть воспроизводимо после изменения модели | Какие версии входят в запрос, ответ и аудит; срок доступности прежней версии |
| Идемпотентность административных команд | Клиент повторяет запрос после неизвестного результата | Область ключа, срок хранения, конфликт параметров и повторный ответ |
| Оптимистическая проверка версии | Несколько администраторов меняют одну сущность | Как обнаружить и показать конфликт; допустимы ли автоматические повторы |
| Явный результат вычисления | Нужно различать запрет, ошибку и нехватку данных | Контракт результата; отображение в API и поведение точки enforcement |
| Кэширование решений или фактов | Измеренная задержка или нагрузка требует кэша | Ключ, границы применимости, отзыв доступа, TTL, инвалидирование и цена устаревания |
| Transactional outbox | Подтверждена необходимость атомарно изменить БД и отправить событие | Гарантии доставки, дубликаты, порядок, повторная обработка и эксплуатационная стоимость |
| Разделение чтения и записи | Измерена потребность в разных моделях чтения/записи | Допустимая задержка проекции, восстановление и сложность поддержки |
| Снимок входных данных | Решение должно объясняться при изменяющихся атрибутах/связях | Минимальный состав снимка, чувствительные данные, срок хранения и согласованность |

DDD, Hexagonal Architecture и другие стили могут быть предложены в ADR с конкретным
обоснованием. Пока они не считаются обязательной организацией кода Tamarix.
Границы ответственности рассматриваются отдельно в [архитектуре сервисов](service-architecture.md).

## Рекомендации: не смешивать модели доступа неявно

- Для каждого сценария указать, какие роли, атрибуты, связи и политики участвуют в решении.
- В T-1 приоритет запрета принят внутри модели и в цепочке; для других
  конфликтов и композиции движков RBAC/ABAC/ReBAC требуется отдельное решение.
- Не выводить принадлежность субъекта, объекта или контейнера из непроверенного ввода.
- Для T-1 сохранять принятое дерево, единственных держателей, области ссылок
  и весь путь моделей от корня до держателя объекта. Способ исполнения T-1
  принят отдельным review в ADR 0002; прочие паттерны не принимаются автоматически.
- Для связей ReBAC определить направление, тип и допустимость циклов; правила обхода — TBD.
- Для атрибутов ABAC определить источник, актуальность, тип и обработку отсутствующего значения.
- Для RBAC определить область роли и назначения; глобальность роли не предполагается.

Эти пункты описывают вопросы design, а не подтвержденную модель данных.
Детали хранения и целостности: [архитектура данных](data-architecture.md).

## Рекомендации: проходить SDD от контракта к реализации

1. В центральном store найти существующую capability и действующие требования сценария.
2. Прочитать нужные документы context и указать противоречия или отсутствующие решения.
3. В design отделить факты от предлагаемого решения и перечислить альтернативы.
4. При влиянии на несколько сервисов описать контракт, порядок изменений и совместимость.
5. В tasks связать реализацию и проверки с требованиями и принятыми design/ADR.
6. На review проверить соответствие поведения требованиям, включая отказы и границы доступа.

Пользовательские документы context требуют явного чтения агентом.
Само наличие файлов в `openspec/context/` не означает их автоматическую загрузку OpenSpec.
Подробности процесса: [архитектурные принципы](architecture-principles.md).

## Рекомендации: проверять поведение, а не название паттерна

Для изменения модели доступа полезна матрица сценариев:

| Ось проверки | Примеры вопросов |
| --- | --- |
| Разрешение/запрет | Есть ли положительный пример и пример доступа вне разрешенной области? |
| Граница данных | Что происходит с неизвестным субъектом, объектом, атрибутом или связью? |
| Изменение состояния | Когда изменение назначения или политики начинает влиять на решение? |
| Конкуренция | Как обрабатываются одновременные изменения и повтор команды? |
| Отказы | Как ведет себя вычисление при недоступности источника данных или неполном контексте? |
| Совместимость | Может ли прежний клиент работать во время обновления контрактов? |
| Воспроизводимость | Достаточно ли версии и входных данных для объяснения результата? |

Список тестов должен соответствовать реальному риску изменения. Для ядра T-1
принят pytest с параметризованными именами сценариев specs и сквозными тестовыми
адаптерами локальных контрактов; инструменты runtime-интеграции остаются TBD.
Контракты результата обсуждаются в [API conventions](api-guidelines.md),
а поведение при отказах — в [security](security.md).

## Рекомендации: фиксировать принятие через ADR

Для значимого решения создать или обновить запись по [правилам ADR](adr/README.md).
Минимальное содержание: проблема, ограничения, альтернативы, решение, последствия,
проверка результата и ссылки на затронутые OpenSpec changes/capabilities.
После утверждения обновить статус соответствующего пункта контекста и поставить ссылку на ADR.
Без явного принятия пользователем или результата review решение сохраняет статус рекомендации/TBD.
