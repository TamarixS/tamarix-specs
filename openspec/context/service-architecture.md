## Разделение ответственности: принятое в T-1 и остальные рекомендации

Источник — прямые ответы пользователя 2026-10-09, приведённые в
[ADR 0001](adr/0001-t1-service-boundaries-and-admission.md), и
[design T-1](../changes/archive/2026-10-13-t-1-container-definition/design.md).
Карта задаёт ответственность за предметные операции и факты; она не выбирает
транспорт, топологию БД, общее хранилище или runtime-адаптеры.

| Сервис | Ответственность и статус | Что не присваивать автоматически | Основные TBD |
|---|---|---|---|
| `container-adm-api` | Установлено в T-1: авторитетное дерево, типы, ключи, привязки DN и отношения контейнеров | Администрирование всех сущностей, хранение всех данных или готовую PKI | API, хранение и доверие |
| `db-control` | Установлено: единственный владелец DDL и Alembic-миграций PostgreSQL | Владение всеми предметными данными, хранение всех данных, runtime-доступ сервисов через него | Deploy-time инструмент или runtime-сервис; эксплуатационный исполнитель, порядок и среда запуска миграций |
| `entity-subject-adm-api` | Установлено в T-1: администрирование субъектов и их единственных держателей, факты о субъектах | IdP, PKI или вычисление решения доступа | Виды/атрибуты субъектов, lifecycle, хранение и API |
| `entity-object-adm-api` | Установлено в T-1: администрирование объектов и их единственных держателей, факты об объектах | Владение содержимым внешних ресурсов или деревом containers | Виды объектов, внешний ID, lifecycle, хранение и API |
| `policy-adm-api` | Установлено в T-1: модели, держатели, ссылки на сущности, проверка областей ссылок и полный набор моделей заданных контейнеров | Движок/язык политик, вычисление итогового доступа или источник всех атрибутов | Версионирование, review/публикация, хранение и API |
| `policy-decision-api` | Установлено в T-1: сбор полной цепочки и вычисление доступа субъекта | PEP, выбранный AuthZEN endpoint или право изменять политики | Wire-модель запроса/ответа, адаптеры, актуальность и SLO |
| `access-assignment-api` | Установлено: T-1 не затрагивает сервис; управление назначениями/связями вне T-1 остаётся рекомендацией | Все отношения ReBAC, роли, политики или единое хранилище графа | Виды назначений, область действия, срок, отзыв, граница с policy |

Административные сервисы проверяют область управления по фактам сервиса
контейнеров и собственным данным о держателе управляемой сущности/модели.
`policy-adm-api` использует факты entity-сервисов для проверки ссылок.
Контейнеры — держатели, а не владельцы сущностей; сервисная ответственность
не изменяет единственного контейнера-держателя.

Для управления принято `O ≼ C ≼ D`: подтверждённый владелец представляемого
`O` адресует `C` в своём поддереве, а держатель управляемых данных `D`
находится в поддереве `C`. Сведения о дереве должны отражать фактическое
родство, включая пропуски типов и исключение соседних веток. Способ вычисления
структурных отношений и проверки до изменения принят в
[ADR 0002](adr/0002-t1-logical-core.md); защита при конкуренции требует
отдельного решения до runtime-интеграции.

## Принятые локальные интерфейсы T-1

Пользователь 2026-10-09 ответил «Да, принять интерфейсы» на
[logical-contracts.md](../changes/archive/2026-10-13-t-1-container-definition/logical-contracts.md);
решение зарегистрировано в ADR 0003. Для каждого из пяти проектов ядра принято
размещение собственных `facts.py / ports.py / core.py` под `src/<package>/`.
Порты описываются Protocol; общий runtime-пакет и импорты внутренних типов
соседнего сервиса не вводятся. Адаптеры преобразуют значения локальных контрактов.

Поставщик дерева различает CompletePath/UnknownPath; поставщик моделей —
CompleteModelSet/UnknownModelSet с явным набором каждого контейнера, включая
пустой. Допуск подтверждает вызывающего либо отклоняет запрос. Вычислитель
отдельной известной модели возвращает Allow/Deny/Neutral/Undefined.
Неуспех обязательных entity-фактов не маскируется под Undefined модели.

Эти результаты задают логический контракт полноты и предметных операций.
Wire API, межсервисный транспорт, PKI/доверие, хранение и конкурентная
согласованность остаются TBD до runtime-интеграции. Тестовый адаптер сам по
себе не подтверждает реальные источники и сертификатную аутентификацию.

Названия сервисов сохраняются в единственном числе там, где это уже установлено;
переименование capability в `entities/subjects` не переименовывает сервис.

## Взаимодействия — принятая семантика и вопросы design

В T-1 источники дерева, сущностей и полного набора моделей назначены выше.
`policy-decision-api` проверяет полный путь от корня до держателя объекта и
полный набор моделей его контейнеров. Неизвестный состав даёт запрет;
неопределённость результата отдельной известной модели нейтральна. Политика
отказов подробно приведена в [security](security.md) и ADR 0001.

Ни один из этих потоков не утверждает конкретные вызовы или транспорт.
Остальные рекомендуемые потоки для обсуждения:

1. Административная операция проверяет полномочия администратора, валидирует
   изменение, сохраняет его и оставляет аудируемую запись.
2. Опубликованные политики, назначения и сведения о сущностях становятся
   доступны вычислению решения. Способ доставки, snapshot/version и допустимый
   лаг — TBD; прямой доступ к чужим таблицам не считать выбранной интеграцией.
3. Потребитель решения передаёт субъект, объект, действие и контекст. Компонент
   принятия решения использует доверенные сведения и возвращает результат.
4. PEP применяет результат в точке защищаемой операции. Размещение PEP и PIP
   внутри/вне Tamarix — TBD; [определения](security.md) не являются deployment map.
5. Изменение назначения/политики и отзыв доступа должны иметь согласованную
   семантику видимости для PDP и кэшей; она описывается в change до реализации.

Для каждого нового взаимодействия в design рекомендуется указать инициатора,
владельца контракта, источник истины, синхронность, ошибки, таймаут, повторы,
идемпотентность, security и порядок обновления сторон. FastAPI для REST API
уже выбран; конкретные контракты и наличие REST-вызова между сервисами требуют
design. Не выбирать Kafka, shared DB или асинхронную репликацию только для
заполнения этой схемы.

## Связь с capabilities

`entities/subjects`, `entities/objects`, `containers` и
`authorization/access-check` затрагиваются в T-1 согласно принятой карте.
`containers` сохраняет один уровень; `authorization` охватывает только
проверку доступа субъектов. Нормативное поведение находится в delta specs
change до его синхронизации с основными specs. `access-model` остаётся
группирующим доменом; не превращать имена policy/access-assignment сервисов в
новые capabilities. В proposal перечислять только фактически затронутые пути
и репозитории; отсутствие capability для новой области явно отметить.
