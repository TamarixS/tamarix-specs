# Integration/e2e и регресс Tamarix

## Решение и состояние реализации

Пользователь 2026-10-14 запросил процесс создания integration/e2e тестов
в отдельной репе с включением в регресс при архивировании OpenSpec, затем
ответил «добавь» на предложенную схему. Процесс принят в
[ADR 0004](adr/0004-testing-regression-lifecycle.md); задачи внедрения — в
[t-2-e2e-tests](../changes/t-2-e2e-tests/).

Реализация `t-2-e2e-tests` добавляет отдельную локальную Git-репу `TamarixTests`,
registry/runner, отчёты, promotion и обёртку archive. Команды и форматы описаны в
[TamarixTests/README.md](../../../../TamarixTests/README.md) и
[tools/ARCHIVE_GATE.md](../../tools/ARCHIVE_GATE.md); CD manifest/readiness и
внешний запуск — в [EXTERNAL_TESTS.md](../../../../TamarixCD/ci/EXTERNAL_TESTS.md).
CI-валидатор проверяет предоставленные archive-артефакты без запуска тестов.
Наличие обязательного check в реальной merge policy подтверждается отдельным
evidence задачи 4.3. Архивы T-1 сохраняются как исторические снимки; обратное
заполнение тестов оформляется новым change.

## Владение и уровни тестирования

| Репозиторий | Ответственность |
| --- | --- |
| `tamarix-specs` | Предметные specs/changes/tasks, критерии приёмки, test-plan, ссылки на тесты, verification/evidence и правила допуска archive |
| `TamarixTests` | Предметные межсервисные integration/e2e, API-клиенты, fixtures, тестовые данные, `registry.yaml`, отбор и runner |
| Репозитории сервисов | Unit/component тесты собственного ядра и адаптеров |
| `TamarixCD` | Сборка/запуск/доставка, собственные тесты и smoke, readiness, manifest среды, вызов внешнего runner и публикация результатов; CD changes локальны |
| `db-control` | DDL и Alembic-миграции; тестовая репа не создаёт собственную схему или миграции |

Integration проверяет взаимодействие компонентов на явно названной границе.
Интеграция реальных Python-ядер через контролируемые адаптеры допустима, но
не подтверждает сеть, реальное хранилище или PKI. E2e проверяет предметный
сценарий через публичные контракты запущенной системы с реальными зависимостями
в заявленном scope, без прямых вызовов ядер или подмены проверяемой границы.
Регресс — назначение и режим отбора тестов, а не дополнительный уровень.
В design обосновывать нужные уровни для каждого критерия, не требовать
дублирования каждого unit-сценария на всех уровнях.

Текущий срез: [контрактные тесты](../../../policy-decision-api/tests/contracts/test_t1_flow.py)
соединяют ядра в памяти. [CD runtime](../../../../TamarixCD/runtime/src/tamarix_runtime/app.py)
объявляет только `/health`; [CD verify](../../../../TamarixCD/verify.py)
подтверждает запуск и health пяти контейнеров. Предметный HTTP e2e требует
бизнес endpoints и реальных адаптеров в соответствующем change.

## Русские описания всех тестов

По дополнительному указанию пользователя все автоматизированные тесты
проекта MUST иметь содержательное описание на русском языке. Правило
применяется ко всем уровням и репозиториям: unit/component/contract,
integration/e2e, регресс, CD/smoke и тесты самой инфраструктуры.

Из описания должно быть понятно:

- Какое поведение/сценарий проверяет тест и при каких исходных условиях.
- Какой наблюдаемый результат ожидается.
- Для чего применяется проверка: какое требование, риск или ошибку она контролирует.

В Python описание хранится в docstring тестовой функции/метода рядом с кодом.
Различающиеся параметризованные случаи поясняются по-русски; общий docstring
и явная таблица/соответствие параметров описаниям допустимы. Одного технического
имени или фразы «проверяет корректность» недостаточно. Test ID, имена функций,
параметров и пути могут оставаться техническими, переименовывать их не требуется.

В TamarixTests русское описание также хранится в `description` записи registry
и выводится в отчёте runner, чтобы назначение случая было понятно без чтения кода.
Docstring, registry и фактическая проверка должны соответствовать друг другу.
Наличие/непустое значение description проверяет registry validator,
русский docstring реальной функции — коллекция runner;
ясность и соответствие смыслу проверяются при review. До включения в регресс
описание обязательно проверяется. Отсутствующие описания существующих тестов
фиксируются открытыми задачами в репозиториях владельцев; CD-задачи планируются
локально. Добавление правила не подтверждает, что прежние тесты уже описаны.

## Размещение и прослеживаемость

Текущее устройство `TamarixTests`:

```text
TamarixTests/
├── openspec/config.yaml    # только store: tamarix-specs
├── AGENTS.md
├── pyproject.toml
├── uv.lock
├── .python-version
├── registry.yaml
├── tests/integration/
├── tests/e2e/
└── fixtures/
```

Конкретное расположение checkout/remote и совместимые pins фиксируются при
создании репы; действующие pins сервисов не обновляются автоматически.
Предметные test-plan и tasks размещаются в центральном change. Для начала
используется существующая `spec-driven` схема; отдельная custom schema не нужна.

Каждый новый/изменённый критерий MUST иметь связь:

`spec path + точные Requirement/Scenario + критерий → стабильный test ID → repo + файл + pytest node ID`.

Параметризованные случаи имеют точный case ID. До реализации допустимы
планируемые ссылки; перед закрытием используются реально собранные тесты.
Один критерий может проверяться несколькими тестами, один тест — несколькими
критериями. Наличие связи проверяется вместе с коллекцией и результатами,
а не только поиском имени файла или процентом покрытия кода.

Пример целевой записи; приведённый test path пока не существует:

```yaml
cases:
  - id: access-empty-chain-denied
    description: |
      Проверяет, что при пустой цепочке моделей результат проверки доступа — Deny.
      Применяется для защиты правила «запрет по умолчанию» от случайного разрешения доступа.
    level: e2e
    state: candidate
    introduced_by: "<change-id>"
    test: tests/e2e/authorization/test_access_check.py::test_empty_chain_denied
    links:
      - spec: openspec/specs/authorization/access-check/spec.md
        requirement: "Запрет по умолчанию"
        scenario: "Пустая цепочка моделей"
        criterion: "<критерий из Scenario>"
```

`registry.yaml` — источник отбора integration/e2e в runner: `candidate`
запускается для своего change, `regression` — в постоянном наборе,
`retired` — исключён по согласованному изменению требований с сохранением
причины/change. Promotion изменяет состояние записи и фиксируется commit;
исходники остаются на постоянных путях, не копируются в `regression/` или архив.

## Запуск по требованию и отчёты

По дополнительному указанию пользователя тесты MUST запускаться по требованию
и формировать отчёты выполнения. Явным требованием считается команда/запрос
пользователя, ручной CI job или проверка в рамках уже согласованной задачи.
Повторное подтверждение согласованного запуска не требуется. Не добавлять
фоновые/периодические прогоны и триггеры commit/старт сервисов/archive без
отдельного требования. Реальные команды runner и output-dir описаны в
README тестовой репы; результаты внедрения — в verification change.

Runner поддерживает выбор конкретных test ID, случаев change, уровня
integration/e2e или всего регресса. Регресс можно запустить без активного change,
повторить прогон и выбрать каталог результатов. Фактический набор фиксируется
в отчёте; пользователь видит, что именно было запущено. Произвольный выбор
для диагностики не заменяет полный обязательный набор допуска archive.

Каждый инициированный прогон получает уникальный run ID и отдельный каталог
результатов, например `reports/<run-id>/`. MUST сохраняться:

- `summary.md`: понятная сводка на русском — что запрошено/выполнено, общий
  итог, счётчики, длительность, ошибки и пути/ссылки на подробные результаты.
- `results.json`: машиночитаемый отчёт с run ID, инициатором/командой и выбором
  набора, timestamps начала/окончания с timezone, длительностью, manifest/hash
  и фиксированными версиями, запрошенными/собранными/выполненными случаями.
  Для каждого случая — test ID/node ID, русское описание, статус/длительность,
  ошибка и ссылки/hash артефактов. Коллекция без выполнения отмечается явно.
- JUnit XML для интеграции с CI, когда требуется выбранной платформой;
  он дополняет русский и JSON отчёты. Логи и диагностика сохраняются по
  применимости, без секретов.

Отчёт создаётся и при FAIL/ошибке коллекции или среды/отмене, а не только
после успеха. Для случаев, не начавшихся из-за ошибки/отмены, используется
`NOT_RUN`, отличный от `SKIP`; ошибка среды не выдаётся за провал предметного
assertion. Все обязательные случаи допуска archive должны иметь PASS;
fail/error/skip/xfail/xpass/NOT_RUN или неполный отчёт не подтверждают успех.

Сведения о прогоне сохраняются до выполнения первого теста и обновляются
по мере исполнения. При обычной отмене runner завершает отчёт со статусом
отмены; при аварийном завершении сохраняется последний неполный снимок,
который gate отклоняет. Отсутствие отметки завершения не считается PASS.
Новый прогон не перезаписывает старые результаты/evidence. Каталог отчётов
задаётся runner, тяжёлые артефакты по умолчанию не коммитятся в specs store;
verification/evidence содержит устойчивые ссылки и контрольные суммы.

Archive/CI gate проверяет уже предоставленный отчёт для нужных revisions
и полного набора. Сам archive не запускает тесты неявно. Если отчёта нет,
он устарел или неполон, change остаётся активным с указанием нужного прогона.
Отдельный явный запрос тестов может быть выполнен до archive в той же сессии.

## Цикл предметного change

1. До реализации описать критерии приёмки в delta specs; основной, негативные
   и граничные случаи включать по применимости.
2. В `test-plan.md`/`tasks.md` центрального change указать уровни, связи,
   русские описания тестов, fixtures, версии, зависимости и проверяемый результат каждой задачи.
   Изменения orchestration оформлять локальным change `TamarixCD` и ссылаться
   на его результат, не переносить CD planning сюда.
3. Реализовать тесты в постоянных каталогах `TamarixTests`, зарегистрировать
   `candidate`; использовать изолированные данные с подготовкой и очисткой.
4. По требованию через CD подготовить среду, подтвердить readiness и запустить
   новые случаи вместе с текущим регрессом для целевых версий, сформировать
   отдельные отчёты выполнения. Новое поведение проверяется
   совместно с согласованными изменениями/выводом устаревших проверок.
5. Сохранить фактические команды и результаты в tasks/verification/evidence.
   Зафиксировать promotion, проверить окончательный commit тестовой репы
   и успешный полный набор; evidence от предыдущего commit не переиспользовать.
6. Только после выполнения условий допустить `openspec archive`. При отказе
   проверки change остаётся активным, соответствующие tasks открыты.

## Evidence и условия archive

Для обязательных случаев MUST быть подтверждены:

- Содержательное русское описание проверяемого поведения, ожидаемого результата
  и назначения теста в docstring, а для TamarixTests также в registry/отчёте.
- Полнота связей каждого затронутого критерия, уникальность test ID,
  существование конкретного node ID при коллекции и попадание в нужный набор.
- Успех новых случаев и текущего регресса; ноль тестов, отсутствующий отчёт,
  skip/xfail обязательного случая или успех одного `/health` не считаются PASS.
  Для первого внедрения пустой прежний регресс обозначается как bootstrap;
  обязательные новые случаи всё равно MUST существовать и пройти.
- Фиксированные commits всех задействованных сервисов, тестовой репы и CD,
  исходная revision store и hashes проверенных specs/deltas, image digests,
  миграции и версия среды. Неприменимые образы/миграции обозначаются явно.
- Идентификатор/время прогона, manifest адресов/версий/изоляции, команды,
  результаты по test ID/node ID, ссылки и контрольные суммы CI-артефактов.
  Русская сводка и JSON отчёт MUST соответствовать одному завершённому прогону;
  выборочный диагностический запуск не подтверждает полный обязательный набор.
  В evidence не сохраняются токены, приватные ключи или секреты доступа.
- Зафиксированное включение нужных test ID в `regression` и актуальность
  ожидаемого поведения относительно целевых основных specs.

Исходную revision/spec hashes проверять по входу прогона: archive сам изменяет
store, поэтому его итоговый commit не может быть входным commit того же прогона.
Результаты для плавающей ветки или другого test/service/CD commit недопустимы.
Исторические evidence остаются историческими; будущий прогон пишет новый отчёт.

Обёртка archive MUST отказать до обновления specs/перемещения change при
невыполнении условий. Обязательная CI-проверка `tamarix-specs` MUST также
проверять commits с архивированием, чтобы прямой `openspec archive` не обходил
процесс. `operations.archive.guidance`, artifact rules, AGENTS и наличие
verification-файла являются инструкциями, не исполняемым gate.

Promotion в тестовой репе и archive в store — разные Git-операции. Сохранять
идентификатор операции, выбранные revisions и состояние шагов; повторный
запуск продолжает проверенную операцию без дублирования записей. Если promotion
уже зафиксирован, а archive не завершён, change остаётся активным; это состояние
отражается в evidence. Изменение входных revisions требует нового прогона.

## Эволюция регресса

- `ADDED`: новые проверенные случаи добавляются в постоянный набор.
- `MODIFIED`: обновляются критерии, ожидаемые результаты и связи тестов;
  прежняя версия сохраняется в Git, а не запускается как актуальное требование.
- `RENAMED`: обновляются spec/Requirement/Scenario ссылки; стабильный test ID
  сохраняется, если смысл проверки не изменился.
- `REMOVED`: случаи выводятся в `retired` только по согласованному change;
  история, причина и проверки совместимости сохраняются по применимости.

Регресс отражает актуальные основные specs, а не неизменяемую сумму архивов.

## Реализация и открытые границы

`TamarixTests` использует Python 3.15.0, uv/uv_build 0.12.24, pytest 9.1.1,
PyYAML 6.0.3 и установленные пакеты пяти ядер 0.1.0; зависимости зафиксированы
в uv.lock. Registry v1, runner, promotion, отдельные JSON/русские отчёты,
CD manifest v1 и archive gate реализованы. Фактические прогоны и merge policy
подтверждаются verification/evidence, а не наличием инструкции или workflow.
Тяжёлые локальные артефакты находятся в игнорируемых каталогах reports;
manual CI должен сохранять весь каталог прогона. Remote тестовой репы пока
не назначен: локальное размещение не подразумевает выдуманный GitHub URL.
Бизнес HTTP/PKI/storage контракты остаются отдельными решениями. До их появления
недоступные e2e критерии оставлять открытыми, не заменять предметный e2e smoke.
