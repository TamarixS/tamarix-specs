# API conventions

Статусы — в [README](README.md). Установлены предметная область и статус
рассмотрения AuthZEN; для REST API утверждён FastAPI, для валидации и
сериализации — Pydantic. Конкретных wire API-контрактов в проекте пока нет.
Локальные Protocol логического ядра T-1 приняты в
[ADR 0003](adr/0003-t1-python-environment-and-contracts.md) и реализованы;
результаты проверки — в [tasks T-1](../changes/archive/2026-10-13-t-1-container-definition/tasks.md).
Следующие conventions — рекомендации для design/review, не утверждённый API.

## Установлено

- Сервисы из [service-architecture.md](service-architecture.md) входят в состав
  Tamarix. FastAPI для REST API и Pydantic утверждены решением пользователя
  от 2026-10-08; имена `*-api` не подтверждают реализацию, JSON или конкретные routes.
- AuthZEN рассматривается для взаимодействия авторизации. Принятие, профиль,
  обязательные операции и версия для Tamarix — TBD.
- Основные specs subjects/objects остаются заготовками; единственные держатели
  и их сохранение приняты в delta T-1. Это не выбирает CRUD, URL, wire-поля или
  коды ответа.
- [ADR 0001](adr/0001-t1-service-boundaries-and-admission.md), принятый по ответам
  пользователя 2026-10-09, фиксирует ответственность T-1, достаточность
  сертификата + зарегистрированного DN→`O` и запрет при неизвестном составе
  цепочки. Wire API и техническое доверие этим не утверждены.

## Рекомендуемое содержание контракта

| Область | Предлагаемое соглашение / проверка | Решение TBD |
|---|---|---|
| Назначение | Различать управление, проверку доступа и применение результата; первые два вида приняты в T-1 | Конкретные wire-операции и PEP |
| Именование | Единый словарь subject/object/resource/action/assignment; описать mapping | Имена wire-полей, routes, регистр |
| Идентификаторы | Документировать scope, формат, уникальность, стабильность и внешние ID | UUID/числа/строки, tenant scope |
| Представление | Типы, required/optional, missing/null, ограничения, примеры | Формат и сериализация |
| Время | Явные timezone, precision и единицы duration | Конкретный формат и правила округления |
| Списки | Стабильная сортировка, предел размера, семантика фильтра/страницы | Cursor/offset, поля сортировки, лимиты |
| Изменения | Валидация, конкурентные обновления, защита от потери изменений | Версии ресурсов, conditional updates |
| Идемпотентность | Различать повтор чтения, записи и вычисления; определить duplicate handling | Ключ, область, TTL и конфликт payload |
| Ошибки | Машинный код и безопасное описание; отделять transport/system error от бизнес-результата | Модель ошибок и отображение в transport codes |
| Решение доступа | Отдельно описать permit/deny и обработку невозможности вычислить решение | Wire-модель, explain, obligations, missing attributes |
| Совместимость | Правила добавления/удаления полей, enum, deprecation и перехода потребителей | Версионирование, сроки поддержки |
| Async | Если требуется: correlation, ordering, retries, dedup, результат и DLQ | Сам факт использования событий и брокер |
| Наблюдаемость | Correlation/request ID без секретов; измерять latency и ошибки | Заголовки/поля, trace transport, SLO |

Для утверждённого REST API на FastAPI рекомендуется закрепить методы и коды
статуса по их семантике, media types, правила TLS и аутентификации, именование
ресурсов. Версию/профиль OpenAPI и место контракта в репозитории-владельце
согласовать отдельно; выбор FastAPI не утверждает конкретную схему контракта.

## Decision flow и безопасность

Рекомендуется описывать субъект решения отдельно от аутентифицированного
вызывающего клиента: право вызвать PDP не означает право подменять субъект,
tenant или доверенные атрибуты. Отказ авторизации и отказ вычисления решения
имеют разную семантику, даже если согласованная политика PEP в обоих случаях
блокирует доступ. Не назначать коды 401/403 или поле `decision` без контракта.

Для T-1 предметная административная модель уже принята: подтверждённый
сертификатом и DN→`O` владелец управляет моделями/сущностями при `O ≼ C ≼ D`
и сохранении инвариантов. Дополнительная административная роль не требуется.
Это не предоставляет доступ переданному субъекту.

При проверке T-1 неизвестный полный путь или полный набор моделей даёт именно
запрет, включая известное разрешение доступной части. Неопределённый результат
отдельной известной модели при установленном составе нейтрален; разрешение +
неопределённость без запрета даёт разрешение. Общее различение отказа и ошибки
не заменяет эту согласованную семантику. Wire-представление, диагностика,
HTTP-коды и техническая аутентификация — [TBD](security.md).

Аудит и административные операции вне этой области остаются рекомендациями
для последующего согласованного дизайна.

## AuthZEN: рассматриваемый стандарт

Для анализа использовать [официальную Authorization API 1.0](https://openid.net/specs/authorization-api-1_0.html)
и [страницу рабочей группы](https://openid.net/wg/authzen/). Стандарт описывает
обмен запросами и решениями между PEP и PDP; язык политик и внутреннее хранение
PDP остаются вне его области. Это характеристика внешнего стандарта, а не
принятое решение Tamarix.

Перед принятием рекомендуется подготовить ADR с такими вопросами:

1. Какую редакцию/профиль поддерживаем и какие evaluation/search/metadata
   возможности действительно нужны? Не вводить endpoints по примеру стандарта.
2. Как отображаются Tamarix subject/object/action/context на модель стандарта,
   особенно идентификаторы, атрибуты и namespaces?
3. Какие особенности RBAC/ABAC/ReBAC видны потребителю, а какие остаются
   внутренними? Как отделяется administrative API от decision API?
4. Как защищается сам API, определяется доверие к сведениям, обрабатываются
   ошибки и обеспечивается совместимость?
5. Какие проверки подтверждают заявленный профиль совместимости? Не заявлять
   conformance только на основании похожего JSON.
